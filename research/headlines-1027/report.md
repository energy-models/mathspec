# Silent wrong answers drive the new headlines

The strongest new headline material is about whether modellers can trust the answer, not about speed. Speed is already covered by the existing headlines. Across Pyomo, linopy, SpineOpt, Calliope and otoole, independent users report two things. Errors surface as tracebacks from deep inside the stack. Worse, mismatched labels are accepted and the solver reports "optimal" on the wrong model. mathspec's load-time refusal, with a suggested rewrite, answers both, so these two headlines rank first. Next come specsolve's **archive** and **queryable run directory**: regulators (AEMO, the Irish SEM Committee, the UK AQuA Book) and production users ask for runs they can reproduce and compare, and those two features deliver exactly that. Rolling horizons with carried state, declared missing-row semantics, diffable formulations and licence-free reading of the math follow, each with a partial fit. Three recurring pains are **gaps, not headlines**: units, infeasibility diagnosis, and NaN/inf checks on supplied data. Treat much of the 2026 linopy/PyPSA evidence and an Oct–Nov 2026 OSeMOSYS/FINE/Temoa cluster as interested or systematic sources, not independent demand (see the section on evidence quality).

## Trust in the answer: headlines 1 and 2

### 1. "Every error names the fix, for you and your coding agent." (mathspec)

- **Pain:** a wrong model produces a traceback from deep in the stack instead of naming the key or dimension at fault.
- **Evidence:**
  - Pyomo, 2019-09-26: new users are "extremely confused when they try to make a `Param` but end up with an unhelpful error message from six function calls deep." ([Pyomo #1126](https://github.com/Pyomo/pyomo/issues/1126))
  - Calliope, 2025-03-19: a mistyped key gives "a very long error message stating that the entire dictionary of parameters defined for each of those technologies is invalid". ([calliope #745](https://github.com/calliope-project/calliope/issues/745))
  - Calliope, 2023-03-17: "If there are excess dims, pyomo receives dataarrays and gives an unrelated error message." ([calliope #420](https://github.com/calliope-project/calliope/issues/420))
  - JuMP maintainers, 2026-06-19: "improving JuMP for coding agents … more informative error messages, so that when things go wrong agents (and users) have more guidance on what to do next". ([JuMP #4175](https://github.com/jump-dev/JuMP.jl/issues/4175))
- **Fit: yes, for the spec.** mathspec refuses misspelt names and dimension mismatches and suggests the rewrite. **Not delivered:** data and config errors, such as a CSV header in the wrong case ([otoole #80](https://github.com/OSeMOSYS/otoole/issues/80)); the capability list says nothing about validating data files. No agent-specific feature exists; the agent claim rests on the same messages.

### 2. "A mismatch is refused at load, never solved to a plausible 'optimal'." (mathspec)

- **Pain:** tools guess when labels or indices do not line up, so the solver returns "optimal" on a model nobody wrote.
- **Evidence:**
  - Pyomo, 2026-10-07, independent user: "I'd expect a `KeyError` to be raised, because `"d"` isn't a valid index … Instead, it continues, returning an empty list." ([Pyomo #4051](https://github.com/Pyomo/pyomo/issues/4051))
  - linopy, 2026-05-02, outside user: "silently map wind to pv and two to one instead of taking the union". ([linopy #670](https://github.com/PyPSA/linopy/issues/670))
  - SpineOpt, 2025-06-24: "If the user is not warned and the optimization silently fails then this has potential create flow on effects which are very expensive (eg. sub-optimal hardware implemented)." ([SpineOpt #1236](https://github.com/spine-tools/SpineOpt.jl/issues/1236))
  - linopy maintainer, 2026-05-21 (**conflict of interest**): "the guesses are sometimes **silently wrong** — no exception, the solver returns `Optimal`". Its "47% too cheap" case is an illustrative scenario, not a production measurement ([PyPSA #1677](https://github.com/PyPSA/PyPSA/pull/1677)). ([linopy #714](https://github.com/PyPSA/linopy/issues/714))
- **Fit: partly.** Delivered: misspelt names and dimension mismatches are refused at load. Not on the list: refusing a *data* label that does not exist (the Pyomo #4051 case) or an unsupported structural combination ([SpineOpt #643](https://github.com/spine-tools/SpineOpt.jl/issues/643)).
- **Overlap:** "check a model before any data exists" sells the timing; this headline sells the consequence avoided. If the two read alike, use this one as the proof line for the existing headline.

## Runs you can defend and compare: headlines 3 to 5

### 3. "Every solve files its own audit record." (specsolve)

- **Pain:** regulators and QA frameworks expect a run to be reproducible later, but tools keep the results apart from the formulation, data and versions that produced them.
- **Evidence:**
  - AEMO's ISP model instructions [snippet]: the 2022 package may not reproduce the published outcomes because confidential data was removed ([2022](https://www.aemo.com.au/-/media/files/major-publications/isp/2022/2022-documents/2022-isp-model-instructions.pdf?la=en)). The 2024 model "may work in other PLEXOS versions" but is untested in them, and AEMO gives no warranties ([2024](https://aemo.com.au/-/media/files/major-publications/isp/2024/supporting-materials/2024-isp-plexos-model-instructions.pdf?la=en)).
  - Irish SEM Committee, 2021 and 2025 [snippet]: NERA validates the SEM PLEXOS model by backcasting against outturn, a recurring regulator exercise. ([SEM-25-010](https://www.semcommittee.com/files/semcommittee/2025-03/SEM-25-010%20SEM%20PLEXOS%20Model%20Validation%202024-2032%20Backcast%20Report.pdf))
  - UK AQuA Book, revised 10 June 2025 [snippet]: requires a "robust version control process"; validation includes "reproducibility"; third-party models are in scope. ([AQuA Book](https://best-practice-and-impact.github.io/aqua_book_revision/analytical_lifecycle.html))
  - PyPSA, 2026-05-19, outside contributor: "We recently migrated to `PyPSA 1.2 (from 0.35)` and observed a delta in the solved model results." ([PyPSA #1681](https://github.com/PyPSA/PyPSA/issues/1681))
- **Fit: yes, for the record.** `archive=` writes the spec, data and answer as parquet, with versions. **Not claimed:** that an upgrade gives the same answer, replay tooling, or mid-run checkpointing. GenX users lose multi-day runs to forced reboots ([GenX #658](https://github.com/GenXProject/GenX.jl/issues/658)), but checkpointing within a run is not on the capability list.

### 4. "Compare a hundred scenarios with one query." (specsolve)

- **Pain:** results land in one file per run, so every comparison loads them all and needs code written for that one comparison.
- **Evidence:**
  - PyPSA, 2026-03-02: "Comparing scenarios requires loading multiple multi-GB files into memory and writing custom pandas code for every query … a bottleneck for production workflows (trading desks, dispatch scheduling, automated reporting)". ([PyPSA #1590](https://github.com/PyPSA/PyPSA/issues/1590))
  - GenX, 2026-05-05: "There is a memory spike when writing results … can cause out of memory issues with large jobs on a HPC." ([GenX #908](https://github.com/GenXProject/GenX.jl/issues/908))
  - JuMP, 2022-09-28: "getting large results feels kind of slow. Fast read of results that can easily be dropped into dataframes, plots, csv etc". ([JuMP #3096](https://github.com/jump-dev/JuMP.jl/issues/3096))
  - FINE, 2026-11-12 (**audit cluster**): the netCDF reader opens one results file "about 50" times. ([FINE #889](https://github.com/FZJ-IEK3-VSA/FINE/issues/889))
- **Fit: yes.** A directory of runs is queried as one set of tables, with sweeps and tidy tables out. Do not reuse #1590's "0.5 s vs 30–50 s": those figures are a proposal, not a measurement. The GenX write-time spike is evidence of the pain only; specsolve's write-time memory is not on the list.
- **Caveats:** #1590's author also filed [linopy #599](https://github.com/PyPSA/linopy/issues/599) and [#740](https://github.com/PyPSA/linopy/issues/740), so this is one vocal production user, not a market signal. The headline overlaps "optimisation as a data pipeline"; this is its query-side proof.

### 5. "Roll the horizon and carry the state, with no hand-fed stages." (specsolve)

- **Pain:** multi-stage and rolling runs either hold every stage in memory or are stitched together by hand, and state or constraints are lost at the seams.
- **Evidence:**
  - GenX, 2026-02-17: "because it retains all model stages in memory this feature is not always practical. Users often run a single stage model and manually feed results forward." ([GenX #904](https://github.com/GenXProject/GenX.jl/issues/904))
  - GenX, 2026-07-17: setting `New_Build=0` in a later stage "causes **all capacity built in prior stages to be lost**." ([GenX #916](https://github.com/GenXProject/GenX.jl/issues/916))
  - ISPyPSA, 2026-11-18: "Custom constraints are not applied when the operational model is solved." ([ISPyPSA #166](https://github.com/Open-ISP/ISPyPSA/issues/166))
  - PyPSA, 2026-11-01 (AI-assisted report): a CO2 cap of 100 run with a rolling horizon "emits 200: each window receives the full cap again." ([PyPSA #2067](https://github.com/PyPSA/PyPSA/issues/2067))
- **Fit: partly.** Delivered: rolling horizons with `carry` of state between windows, and myopic runs. **Not claimed until verified:** that period-wide caps and minimums are split correctly across windows (PyPSA #2067, [#1769](https://github.com/PyPSA/PyPSA/issues/1769)). Temoa's myopic issues ([#395](https://github.com/TemoaProject/temoa/issues/395), [#398](https://github.com/TemoaProject/temoa/issues/398)) belong to the audit cluster.

## Formulations people can inspect: headlines 6 to 10

### 6. "A missing row means what the spec says it means." (mathspec)

- **Pain:** NaN, empty or infinite inputs are filled or summed to zero without a word, and show up later as infeasibility or a wrong result.
- **Evidence:**
  - pypsa-eur, 2026-05-30, outside user: `cluster_heat_buses` "silently sets p_set=0.0 … via NaN-summing aggregation". ([pypsa-eur #2182](https://github.com/PyPSA/pypsa-eur/issues/2182))
  - pypsa-eur, 2026-06-04: "Silent NaN load data when using fixed_year with snapshots from a different year". ([pypsa-eur #2187](https://github.com/PyPSA/pypsa-eur/issues/2187))
  - pypsa-eur, 2024-08-20: "The coke demand for NL is inf leading to an infeasible solution." ([pypsa-eur #1226](https://github.com/PyPSA/pypsa-eur/issues/1226))
  - FINE, 2026-11-12 (**audit cluster**): "If a period is passed as a series of NaN, FINE accepts the model … NaN becomes the variable bounds". ([FINE #890](https://github.com/FZJ-IEK3-VSA/FINE/issues/890))
- **Fit: partly.** Delivered: a parameter declares what a missing row means (`missing:`), and `where:` leaves an entry absent rather than zero-filled. **Gap:** detecting NaN or inf in supplied data is not on the list. Several pypsa-eur cases are preprocessing bugs upstream of any modelling layer.

### 7. "Same data, different answer? Diff the math, not the code." (mathspec)

- **Pain:** model intercomparisons harmonise the inputs and still cannot isolate which equation caused the gap, because each formulation lives in code.
- **Evidence:**
  - Van Liedekerke et al., Dec 2024 [verified], summarising an earlier comparison of four German electricity models: "they harmonize scenario data and show that the result differences mainly depend on the modeling approach." The line is in the paper's introduction, not its abstract, and reports Misconel et al. 2022, not the paper's own Swiss–European results. ([arXiv 2412.12964](https://arxiv.org/abs/2412.12964); [Misconel et al. 2022](https://doi.org/10.1016/j.rser.2021.111785))
  - OSeMOSYS, 2019-10-22: "The situation is complicated somewhat by there being multiple different implementations of OSeMOSYS, in GNU MathProg, GAMS, Pyomo and Pulp." ([OSeMOSYS #97](https://github.com/OSeMOSYS/OSeMOSYS/issues/97)) The GAMS port's "generated constraint set differs from the reference" (2026-10-13, **audit cluster**; [OSeMOSYS_GAMS #5](https://github.com/OSeMOSYS/OSeMOSYS_GAMS/issues/5)).
  - Hoffmann et al. 2024 [abstract]: earlier framework reviews compared features and left out the underlying mathematics. ([DOAJ](https://doaj.org/article/316f10bce49e45f697b7130f71bdc354))
  - ACER on the draft TYNDP 2024 scenarios [snippet]: the draft "still did not fully meet the transparency standards", with no reasoning on how stakeholder observations were handled. ([ACER](https://www.acer.europa.eu/news-and-events/news/acer-calls-improvements-entsos-draft-tyndp-scenarios-comply-its-framework-guidelines-2024))
- **Fit: partly.** A spec is a text file, so ordinary diff and version control apply. PyPSA's model and Calliope's math are both already specs, so two frameworks' formulations sit side by side in one language. **Not on the list:** a semantic diff tool. OSeMOSYS, GenX and Temoa are not written as specs.

### 8. "Read the plan's math without buying a seat." (mathspec, with specsolve to rerun)

- **Pain:** in planning proceedings, a commercial licence decides who may read or rerun the model behind a public decision.
- **Evidence (all [snippet]; re-check before quoting):**
  - Iowa Ethics Board advisory opinion, 2026: Energy Exemplar quoted "$75,000 to $90,000" for the PLEXOS platform and "$20,000 to $25,000" per named user. The notes name it 26-AO-1103, but the link slug reads 26-ao-1096. A search summary says the board's 1 April 2026 notice lists the licence gift as 26-AO-1103 and 26-AO-1096 as a different opinion, so the slug may be mislabelled. The page could not be read, so the number is not settled; cite neither until it is. ([Iowa opinion](https://ethics.iowa.gov/advisory-opinion-26-ao-1096-0))
  - DESC IRP stakeholder FAQ, undated: stakeholders must "sign a limited license", and "the PLEXOS manual cannot be provided without a license". ([DESC FAQ](https://desc-irp-stakeholder-group.com/FAQ/Miscellaneous-Other))
  - LBNL/Synapse IRP best-practice guide for DOE, 2024: calls for "modeling software licenses, paid for by the utility, for all technically sophisticated stakeholders". ([Synapse/LBNL](https://www.synapse-energy.com/sites/default/files/IRP_Best_Practices_2024_Synapse_LBNL_24-061_1.pdf))
  - ETSAP: the TIMES runtime licence "cannot be used to change the model's equations and variables". ([ETSAP](https://iea-etsap.org/getting-started-withtimes-modelling/))
- **Fit: partly.** Reading: yes, a spec prints as LaTeX, Typst and Markdown. Rerunning: specsolve runs HiGHS. **Not on the list:** specsolve's own licence terms, so do not say "free". The regulated plans themselves are PLEXOS models, not specs, and porting them is the real barrier.
- **Overlap:** neighbours "share the formulation without sharing private data". The new angle is *who gets to look*.

### 9. "Custom constraints that travel with the model." (mathspec)

- **Pain:** user constraints are callbacks into the internals, so they are lost on save, skipped in rolling runs and broken by upgrades.
- **Evidence:**
  - PyPSA, 2021-12-09, still open: "Custom constraint and their duals should become a officially supported part of the data model with IO functionality." ([PyPSA #322](https://github.com/PyPSA/PyPSA/issues/322))
  - Calliope, 2018-04-16: a user "can currently add a custom constraint after building the backend model … by accessing the Pyomo ConcreteModel directly via `model._backend_model`." ([calliope #100](https://github.com/calliope-project/calliope/issues/100))
  - PyPSA maintainer, 2026-06-15: reserve constraints "go deep into the logic … Non-proficient users are therefore very much left out". ([PyPSA #1729](https://github.com/PyPSA/PyPSA/issues/1729))
  - ISPyPSA #166 (see headline 5): custom constraints are dropped in the operational solve.
- **Fit: partly.** A fragment is a file, composed with `merge` and `adds_to`, and the archive stores the spec with the answer. Whether PyPSA's own network save keeps it is outside the list.
- **Overlap:** "extend a model without forking it". Merge the two if they read alike. A maintainer's wish for declarative, persistable constraints ([linopy #561 comment](https://github.com/PyPSA/linopy/issues/561#issuecomment-3822631204)) is the `linopy.spec` work itself, so it carries a **conflict of interest**.

### 10. "Pay only for the rows that exist." (mathspec + specsolve)

- **Pain:** dense labelled arrays charge sparse energy models for their empty cells.
- **Evidence:**
  - linopy, 2024-03-07: "Not supporting sparsity hence would increase our model size by ~900x. This effectively prohibits us from using Linopy as is." ([linopy #248](https://github.com/PyPSA/linopy/issues/248)) The author develops pyoframe, a competing tool.
  - PyPSA-Eur user, 2024-04-19: "the non-sparse nature of xarray is also impacting the memory footprint of solving pypsa-eur networks". ([linopy #248 comment](https://github.com/PyPSA/linopy/issues/248#issuecomment-2066113554))
  - SpineOpt, 2024-01-18: "even if many constraints have indices which are a null set, the SpineOpt code to figure that out takes a long time to execute." ([SpineOpt #856](https://github.com/spine-tools/SpineOpt.jl/issues/856))
- **Fit: partly.** `where:` leaves an entry absent, and specsolve works on long tables, which are sparse by construction. No memory figure is on the list, so put no number on the claim. Overlaps "full-size models".

## Conclusion

The pattern has shifted. A 2018-era pitch sold openness and speed. The 2024–2026 complaints are about **plausible wrong answers** and **runs nobody can defend later**, and they come from users of Pyomo, Calliope, SpineOpt and GenX, not only PyPSA. That makes headlines 1–3 the most credible to an audience outside the PyPSA ecosystem. They also rest on capabilities that already ship: load-time refusal with a rewrite, and the archive.

The regulator evidence is the most commercially interesting and the least verified. Every AEMO, ACER, Iowa and DESC item is a search excerpt, so re-read them before they go into copy. The same pains continue past what mathspec currently checks: units, data values and infeasibility. Building units would turn the best-evidenced gap into the next headline.
